Golden Years — Codex 开发任务文档
版本：1.0
目标平台：Windows 10/11
技术栈：Python 3.11+、PySide6
项目仓库：https://github.com/camkiddeng/Golden_Years

一、总体目标
编写名称为 Golden Years 的本地照片与视频整理桌面程序。用户选择一个主文件夹后，程序只扫描该目录“直接包含”的照片和视频，按 Windows 文件系统的最后修改时间归入“年份/月/Photos或Videos”，对新归档文件按时间排序并顺序编号。发现字节级完全相同的文件时，将多余文件剪切至主目录下固定的 XXX 文件夹并记入当月重复日志。任何情况下不得静默覆盖、删除文件。

二、交付成果
1. 可直接运行的 Python 源代码（建议 main.py + organizer.py，或其他简洁合理的结构）。
2. PySide6 GUI，窗口和任务栏使用项目根目录的 Golden_Years.ico；不要使用旧名称 Paper_Wizard.ico。
3. 根目录 requirements.txt（已有；仅 PySide6 为必需第三方库）。
4. 简要 README.md：Windows 安装、运行、测试方法；推荐 python -m pip install -r requirements.txt 和 python main.py。
5. 使用 Python 标准库 unittest 或 pytest（如选择 pytest，要更新 requirements.txt）编写可执行测试。优先标准库 unittest，减少依赖。
6. 不要求本阶段构建 EXE；可在 README 给出可选的 PyInstaller 打包提示，但不要把 PyInstaller 列为运行必需依赖。

三、扫描范围及支持的文件
1. 只枚举用户所选主文件夹的第一层文件（如 pathlib.Path.iterdir()）；绝不递归寻找待整理文件。
2. 忽略所有目录，尤其是 2026年、2月、Photos、Videos 和 XXX 中的文件，不作为待转移来源。
3. 但是查重“基准库”必须读取主目录下已经归档的规范路径：<主目录>/<YYYY年>/<M月>/Photos 和 Videos 内的文件；仅检查这类路径中的直接文件，不扫描其他任意子目录，也不扫描 XXX。
4. 默认支持照片扩展名（忽略大小写）：.jpg、.jpeg、.png、.heic、.heif、.webp、.bmp、.tif、.tiff、.gif、.dng；视频：.mp4、.mov、.m4v、.avi、.mkv、.wmv、.mts、.m2ts、.3gp。
5. 不支持的扩展名保持原样，不移动；不要依赖媒体解码器、EXIF 或 ffmpeg。
6. 仅以扩展名作类型判断；不改变图片/视频编码，也不修改内容。

四、时间与分类规则（重要）
1. 唯一分类依据是 Windows 文件系统的“修改日期/最后修改时间”（os.stat().st_mtime / datetime.fromtimestamp），按用户电脑当前本地时区解释。不要使用创建日期、EXIF DateTimeOriginal、文件名中的时间，也不要采用上传后的时间。
2. 文件修改时间在执行之前读取并保存为不可变的任务元数据；排序优先按完整时间戳（包括小数秒），相同时间按原文件名 casefold 后排序、再按原文件名排序，以确保结果可重复。
3. 分类路径：<主目录>/<YYYY年>/<M月>/Photos 或 Videos。例如 2026-02-12 的图片放到 2026年/2月/Photos。
4. 不存在内容的年、月、类别文件夹不得预先创建；仅当确实要成功归档该类文件时创建。XXX 只有实际发生重复文件转移且该目录不存在时才创建；已有的直接复用。
5. 归档成功后保留原修改时间（以及尽量保留原访问时间）。同卷重命名通常保留；跨卷移动须在完成后用 os.utime 恢复。严禁因分类或重命名意外改变修改时间。
6. 不改变已归档文件的名称、位置或修改时间；仅把根目录新增文件整理进去。

五、命名与编号
1. 照片：MQPYYYYMM_NN.<原扩展名>，视频：MQVYYYYMM_NN.<原扩展名>。
2. YYYY 为四位年份，MM 为两位月份；序号至少两位：01、02……99、100……，不可在 99 截断。
3. 每个年月与类别独立计数；扫描该目标 Photos/Videos 文件夹，识别符合该年月与类别模式的已归档文件（大小写不敏感，序号必须为正整数），从“最大序号+1”继续；没有则从 01 开始。
4. 不填补缺号、不修改任何已有文件名；即使新增照片时间早于已有照片，也只续号，不全量重新排序。
5. 对本次将要归档的文件，分别按年月/类型分组，再按修改时间由早到晚排序，按顺序连续分配编号。照片与视频各自编号。
6. 保持原始文件后缀，不随意转成 jpg/mp4。若拟定目标路径已存在（含大小写冲突），不得覆盖；跳到下一个可用序号。移动之前必须再检查目标不存在，遇到竞态冲突应安全失败或重新分配，不能覆盖。

六、重复文件判定（严格字节级）
1. 重复必须是文件字节内容完全一致，不比较照片的视觉相似度，也不比较解码图像；不同压缩或不同元数据造成字节差异，则不属于重复。
2. 用文件大小预筛选，再按需分块计算 hashlib.sha256，避免把整个大视频加载进内存；同大小、同 SHA-256 后可再逐块比对以彻底确认（建议实现）。
3. 修改时间、文件名与扩展名不参与“是否字节重复”判定。照片与视频可按全部受支持媒体文件统一查重，正式归档的基准文件必须来自规范 Photos/Videos 路径。
4. 先对已归档基准库建立大小索引；本次根目录新增文件之间也必须查重。确定唯一保留件时：
   - 若某新增文件与已归档基准文件相同，保留已归档文件，不更动它；新增文件视为重复。
   - 若本次多个新增文件互相完全相同、且没有已有归档基准，选“修改时间较早者”；若时间相同，则按原文件名稳定排序选一件作为正本，剩余全部视为重复。
   - 基准库中已有的重复文件不自动搬移/改名/删除。可选择第一个按相对路径稳定排序的基准文件作为日志中的对应文件。
5. 严禁使用“修改日期相同 + 文件大小相同”直接断言重复；哈希必须基于真实文件字节。
6. XXX 文件夹不参加查重、不作为正本来源，也不对已有 XXX 文件自动处理。

七、重复文件存放与日志
1. 重复的新增文件只剪切到 <主目录>/XXX，不重命名为 MQP/MQV；尽量保持原始文件名、扩展名和修改时间。
2. 如果 XXX 中存在同名文件，不能覆盖；以 _1、_2 等确定性后缀生成唯一新名称，并在日志中记录最终 XXX 文件名。
3. 正本在正式归档位置（包括本次刚归档的正本）；日志必须记载完整的相对路径和新文件名。
4. 每月日志名以“实际执行时的本地年月”命名：YYYYMM_重复文件日志.txt，例如 202611_重复文件日志.txt；注意这不是照片的拍摄年月或修改年月。
5. 只有本次确实产生至少一条重复转移成功的记录时才创建/追加日志；没有重复，不创建文件，也不清空已有日志。
6. 同月已有日志则使用 UTF-8 编码追加本次记录，不覆盖历史。建议格式包含运行时间、原文件名、XXX 内最终文件名、相对主目录的正本路径、文件大小、SHA-256；可注明错误/未成功移动的记录不属于成功重复数。
7. 为避免数据损坏，只有在重复文件成功移入 XXX 且正本确实存在之后才将其记录为成功重复；日志写入失败必须明确报警，不得显示“日志已生成”的虚假成功信息。
8. 正式归档和 XXX 的任何文件绝不自动删除。

八、安全与错误处理（最高优先级）
1. 操作语义是剪切/移动，而非复制后保留两份。优先 os.rename / shutil.move；跨卷时 shutil.move 可能内部复制再删除，因此必须确保复制成功、校验完成后才移除源文件，不能出现半成品被误认为成功。可以采用临时文件 + 分块 SHA-256 校验 + 原子命名 + 删除原件的安全方案。
2. Windows 同卷移动不得覆盖已有目标；禁止 os.replace 这类覆盖式操作。若跨卷，先复制至目标目录里的独特临时文件，检查大小和哈希匹配，安全提交到尚不存在的最终目标，然后删源文件；任何阶段异常都保留可恢复数据并提示，不默默丢失。
3. 对访问拒绝、文件正在被占用、磁盘已满、路径过长、文件中途变化、修改时间读取失败、相同文件名碰撞等情况捕获异常，继续处理可处理的文件；失败项保留源文件并计入失败数量。
4. 不读取或处理符号链接/目录联接指向主目录之外的文件，以免误操作；基准库路径只限真实的规范目录，不应通过链接跳往别处。
5. 处理前形成稳定的根目录文件清单；在哈希计算和移动前重新检查文件存在且大小、mtime 等与初始快照一致。若处理期间被其他程序修改，跳过并报告。
6. 避免一个任务重复点击执行导致并发处理；工作中禁用“执行”，完成恢复。任务在后台工作线程运行，所有 GUI 更新用 Qt signals/slots，不从线程直接操作 QWidget。
7. 同时记录成功归档照片/视频、重复照片/视频、失败照片/视频、跳过文件数，统计口径清楚；任何失败不得报告“全部成功”。
8. 不要修改主目录里其他无关文件；没有用户确认，不删除任何文件。

九、简洁 UI 规格
1. PySide6 主窗口标题 Golden Years；如果仓库根目录有 Golden_Years.ico，则 QApplication 与主窗口均设置该图标。若图标尚不存在，程序应仍可运行并给出非致命提示。
2. 界面只有文件夹路径展示框、“选择”按钮、“执行”按钮，以及底部只读、可滚动的多行运行结果文本框；可以有最小必要的状态提示，但不要复杂工具栏和多余配置。
3. “选择”使用 QFileDialog.getExistingDirectory；未选目录时禁用执行或提示用户选择。
4. “执行”开始整理；输出当前阶段与最终汇总，例如：
   扫描完成：照片 125，视频 18
   成功归档：照片 118，视频 16
   重复文件：照片 7，视频 2
   失败：照片 0，视频 0
   重复日志：XXX/202611_重复文件日志.txt（已生成）
   全部操作完成
5. 无重复时显示“重复文件：0；本次未生成重复日志”。错误要包含文件名与原因；扫描大量视频时 UI 仍需响应。
6. 可对工作线程提供进度信号，不能将刷新文本框的 GUI 操作放进工作线程。

十、建议实现次序
1. 将核心整理逻辑实现为与 GUI 解耦、可通过临时目录独立测试的函数或类。
2. 实现扫描、时间快照、规范归档目录识别及最大编号查询。
3. 实现重复索引（文件大小 + SHA-256 + 可选最终逐字节确认）及本次新增文件的正本选择。
4. 实现无覆盖、安全移动、时间戳保留、碰撞处理。
5. 实现 XXX、重复日志与清晰统计。
6. 将核心处理接入 PySide6 工作线程与 GUI。
7. 编写和运行测试，再补 README。

十一、必须覆盖的验收测试
A. 仅处理根目录媒体文件，不从任意子目录提取媒体。
B. 2026年2月有图片与视频时创建 2026年/2月/Photos 和 Videos；只有图片则不创建 Videos；完全没有媒体不创建空目录。
C. 以 st_mtime 分类；构造 EXIF 时间、创建时间、文件名时间与修改时间不一致的样本，确认仅按修改时间。
D. 同月照片按 mtime 排序，新文件从 01 开始；目标已有 01、03 时，新文件从 04 开始且原文件保持不变；超过 99 正常变为 100。
E. 多次运行幂等：无新增媒体时不更名、不移位、不新建重复日志。
F. 不同文件名或不同 mtime、但字节完全相同的图片能识别为重复；同大小但内容不同不误判。
G. 与已有正式归档文件重复：只移动新增件到 XXX，日志指向已存在的 MQP/MQV 文件。
H. 本次多个根目录文件互相重复：只归档一个正本，其他移至 XXX，日志指出对应的新文件名。
I. XXX 中同名不覆盖，生成 _1 后缀；XXX 里的文件本身不作为重复基准。
J. 同月重复日志追加，不覆盖以前内容；零重复不创建新日志。
K. 归档及 XXX 转移后修改时间保持一致（容忍文件系统精度差异），源文件消失，目标内容完整。
L. 目标同名、文件占用、无权限、源文件被修改/删除时，不覆盖、不丢数据，并在 UI 显示错误。
M. GUI 能选择文件夹、正确显示阶段/总数，执行期间不冻结，防止二次执行。
N. 无 Golden_Years.ico 时能启动；提供该图标时窗口图标正确。
O. 大视频以分块方式哈希，不一次性读入全部文件。

十二、具体约束与交付自检
1. 此项目面向家庭照片/视频，数据安全优先于速度和代码行数。
2. 不使用云服务、不联网、不上传媒体文件；均为本地处理。
3. 不重新编码、不压缩、不编辑文件内容，不使用 EXIF 作为分类依据。
4. 代码尽量清晰、带必要中文注释，避免过度架构。
5. 提交代码前在 README 中写明已运行的测试、运行命令及已知限制。
6. 不要把真实私人照片/视频提交到 GitHub；测试只用自动生成的虚拟文件。
7. 完成后确认 requirements.txt 与实际导入的第三方模块一致。
8. 用户已明确确认：图标 Golden_Years.ico；严格字节级重复；已有文件保留编号、新文件接最大序号；XXX 不参与查重。

最终验收标准：用户在 Windows 上安装 requirements.txt 后启动 GUI，选择主文件夹，点击执行；程序按修改时间分类、按月续号、移动原文件、将字节级重复移入 XXX 并生成准确日志，且不损坏、不覆盖、不误删任何媒体文件。
